    Critical QuickJS JNI constraints discovered (required for correctness):

    1. globalThis is the only reliable persistent namespace across evaluate() → call() boundaries. Top-level var bindings and function-object properties (e.g. fn._routes = {}) are NOT reliably visible inside functions called via engine.call(). The C helper uses globalThis[fn] — use globalThis.__capsule_routes for shared state.

    2. JS functions called via engine.call must return plain objects, not JSON strings. The C __capsule_call helper wraps every return value in JSON.stringify(). If JS dispatch() returns a pre-serialised string (from JSON.stringify({...})), the result is double-encoded: "{\"jsonrpc\":\"2.0\",...}". The correct pattern is to return the object directly: return { jsonrpc: '2.0', id, result }.

    3. router.ts: dispatch() return type is object | null (was string | null)

    4. Test routerScript: return { jsonrpc: "2.0", id, result } (not JSON.stringify(...))
    5. Exception: production esbuild IIFE bundle is fine — all routes registered inside the IIFE before it returns, closures work correctly within a single evaluate() call.

    Session 2026-06-16 — Phase 3 #1: Filesystem API (Android)¶

    Shipped the Filesystem native API (capsule 083b2cf, examples 18103d8) — the foundational Phase-3 capability, built with the proven interface + provider + Fake pattern across all three layers:

    • @capsule/core — FilesystemModule: readFile / writeFile / appendFile / deleteFile / mkdir / rmdir / readdir / stat / getUri / downloadFile; FilesystemDirectory (data/cache/documents), FileEncoding (utf8/base64), FileEntry/FileStat; FilesystemMethods shared with WebBridge. New error codes 5xxx: FILE_NOT_FOUND / FILE_IO_ERROR / PATH_NOT_ALLOWED.
    • WebBridge dev fallback — localStorage-backed FS keyed by (directory, path), base64-canonical storage with unicode-safe utf8⇄base64, implicit-directory readdir, traversal guard. Methods are async so the synchronous traversal check rejects (per the Bridge.call promise contract) rather than throwing.
    • capsule-android — FilesystemProvider (iOS seam) + AndroidFilesystemProvider over java.io.File, all I/O on Dispatchers.IO, canonical-path traversal guard, downloadFile via HttpURLConnection; filesystemHandlers(...) wired into CapsuleActivity.
    • @capsule/cli — sync.ts now auto-declares INTERNET (normal permission, no dialog) for downloadFile.
    • react-ts example — new Filesystem playground tab (directory toggle + write/append/read/stat/ delete + mkdir/readdir + download).

    OTA-safety constraint (a) honored concretely: roots are filesDir/capsule/fs/{data,documents} and cacheDir/capsule/fs/cache, deliberately not under filesDir/bundles (the OTA swap target) — an instrumented test (rootsLiveOutsideTheOtaBundleDir) asserts the invariant. Constraint (b) native-capability version: deferred by design — no consumer until the Phase-5 OTA server exists; building the gate now would be speculative. Land it alongside Phase 5.

    Full test sweep — all green (2026-06-16): TS unit 91 (@capsule/core; +12 filesystem module, +9 web-bridge fs) · Kotlin JVM unit 85 (+14 FilesystemHandlerTest; testReleaseUnitTest BUILD SUCCESSFUL) · Android instrumented 23 (+10 AndroidFilesystemProviderTest — real encoding round-trips, traversal guard, directory isolation, OTA-safety) on CapsuleTest emulator (API 35) · react-ts example tsc --noEmit clean · release AAR rebuilt clean.

    Review + refactor (same day, capsule f99315b): re-read the Filesystem implementation for smells. Three fixed: 1. getUri contract violation — resolve() did root().apply { mkdirs() }, so the documented "pure, no I/O" getUri (and reads/stat) created the root dir as a side effect. Now resolve() is pure; roots are created lazily only by the write paths (prepareParent/mkdir). 2. Repeated try/catch → FileIoError across 4 provider methods → extracted a single io { } helper (runs on Dispatchers.IO, passes CapsuleException through, maps anything else to FileIoError). Also fixed a case where decode()'s specific error got re-wrapped/lost. 3. Cross-file param-parsing duplication (camera + filesystem each had private string/bool/contentOrNullSafe) → new shared handlers/JsonParams.kt (optString/optInt/optDouble/optBool); both handler sets migrated. Sets the convention for every future API's param parsing. No behavior change intended — verification pending the user's full test run before commit.

    Overall health — good. Phase 3 on track (Camera + Filesystem done, tested release + dev + browser); pattern consistency holding (interface + provider + Fake + DTO); test pyramid healthy. No architectural debt surfaced beyond the three smells above.

    Design note — Share / "save to user-visible location" (discussed, not built): share is a native OS feature everywhere (Android ACTION_SEND share sheet, iOS UIActivityViewController, Web Share API) — Capsule just bridges it; reuses the camera FileProvider. It's the truly cross-platform primitive for "give the user this file," because iOS has no public Downloads folder (its share sheet covers Save to Files/Photos). A saveToDownloads is therefore an Android/web specialization (Android MediaStore.Downloads, web Save-As), not a core API. filesystem.downloadFile is correctly app-private (verified: browser stores under __capsule_fs__:* in localStorage; device under filesDir). Share stays at roadmap Phase 3 #7 unless pulled forward.

    Next: Phase 3 #2 — App lifecycle + deep links (fg/bg events + incoming URLs/universal links; infrastructure that push tap-routing and OTA foreground re-checks both depend on). Share (#7) can be pulled forward on request — it's self-contained and low-risk.

    Browser QuickJS testing — open question¶

    Q: The developer can change Vite to another bundler. Will Option B (Vitest/Jest in Node.js) still work?

    Yes — completely. Vitest tests @capsule/core source directly using its own internal bundler (esbuild). The app's bundler (Vite, Webpack, Rollup, Parcel, esbuild…) is irrelevant. Changing the app bundler has zero effect on the test suite. The 36 TS tests and any future Vitest tests will keep working regardless.

    The only thing that changes between bundlers is the shape of assets/www/index.js (the app bundle). That is tested end-to-end on device, not by Vitest.

    Three browser testing options:

    • A — quickjs-emscripten: run the same C engine as WASM in Node.js — highest fidelity, tests that bundles actually execute in QuickJS before hitting the device
    • B — Vitest + happy-dom ✅ DONE: test WebBridge (browser fallback) in a browser-like environment — bundler-agnostic, no device needed
    • C — Chrome DevTools on WebView: chrome://inspect → connect to device WebView → run bridge calls in devtools console

    Two sub-tasks (both deliver independent value, built together):

    Sub-task A — JSON-RPC file discovery¶

    User creates src/routes/device.getInfo.ts, CLI bundles it, QuickJS intercepts that method before Kotlin. - File: src/routes/<method>.ts (method name = filename without extension) - Handler: export default function handler(params) { return {...} } - CLI auto-discovers files and generates addRoute("method.name", handler) calls - No registration needed — file presence = route registration

    Sub-task B — HTTP API routing¶

    User creates src/server/routes/users.ts, NanoHTTPD routes /api/users to QuickJS. - File: src/server/routes/<name>.ts (path = /api/<name>) - Handler exports: export function GET(req: CapsuleHttpRequest) { return { status: 200, body: '...' } } - NanoHTTPD intercepts /api/* and calls QuickJSEngine.call("handleHttpRequest", ...) - @capsule/core/routes exports CapsuleHttpRequest, CapsuleHttpResponse, addHttpRoute, handleHttpRequest - Framework-agnostic: completely independent of Angular/React/Vue client routing
