    Capsule Framework — Implementation Overview¶

    This folder contains the step-by-step implementation guide for building the Capsule Framework itself — the CLI, native shells, core SDK, and CodeSync infrastructure.

    Prerequisites: machine setup complete (environment.md). GitHub org and CI/CD are Phase 8 (Ecosystem).

    Implementation Phases¶

    Re-sequenced 2026-06-15 (strategy session, revised). Capsule is a personal project — not racing for funding, so capability comes before monetization: native-API expansion stays Phase 3, then iOS, then Capsule UI (native-look layer, Phase 5 — slotted after iOS so its presets target a real iOS shell), then the Server Code Push / OTA cloud (the eventual funding engine, gated on iOS) and the migration on-ramp. The strategy/business docs (../Business/) still hold — they're just sequenced later. The old phase content is preserved; only order changed.

    HTTP fidelity roadmap (embedded server, both platforms — adr-004): the on-device /api server delivers a full web experience, tiered so each step is realistic and works properly:

    Capability Status / phase
    Static serving + request/response /api/* (GET/POST/PUT/DELETE) ✅ Android (Phase 2) · Phase 4 for iOS parity
    Streaming responses (chunked) Phase 4 parity target
    WebSockets (ws://localhost, on-device real-time) ⬜ Future — needs a new core route model (onOpen/onMessage/onClose) + single-thread-engine frame pumping. Designed, not excluded. Not promised in the first iOS cut.
    Server-Sent Events (SSE) ⬜ Future — new core streaming-route model (pairs with WebSockets work)
    Range requests (media seeking) ⬜ Future — server-side Range handling

    These amend adr-001 #4 ("deliberately minimal, no WS/SSE"): HTTP fidelity is now tiered, not minimal-forever. The Bridge-vs-HTTP channel split still holds — WS/SSE are web-standard real-time inside the on-device server, distinct from the native-event Bridge.

    Shell Version Registry (Phase 8)¶

    Phase 1: Use CAPSULE_SHELL_OVERRIDE_PATH to point the CLI at your locally built AAR — no registry needed.

    Template extensibility (Phase 1 init + Phase 8 ecosystem) ✅ 2026-06-12¶

    The CLI's init resolves templates from a single templates repo (subdirs per template), driven by a manifest.json so adding a template needs no CLI release:

    capsule init my-app --template react-ts                  # official (manifest → templates-repo subdir)
capsule init my-app --template gh:acme/capsule-tpl#v2    # any giget source (GitHub/GitLab/Bitbucket/tarball)
capsule init my-app --template ./my-local-template       # local path
    • Dev: reads local templates/manifest.json + copies the subdir.
    • Prod: fetches the manifest from the templates repo (raw URL), giget pulls gh:<repo>/<dir>#<branch>; bundled list is the offline fallback.
    • Custom templates: any source that isn't an official name is passed straight to giget (or copied if a local path). The CLI won't clobber a capsule.config.ts a custom template ships.

    Design decisions (2026-06-12)¶

    Compatibility — what Capsule guarantees, and for how long¶

    • The frontend framework runs in the WebView, NOT in QuickJS. QuickJS only runs server routes (src/routes, src/server/routes) + @capsule/core's router. → Any frontend framework, any version, is fine; the only ceiling is the WebView/browser baseline (tied to minSdk / OS).
    • The one real compatibility surface is QuickJS — server-route code must stay within QuickJS-ng's supported JS feature/API set (no Node/DOM globals).
    • The contract to freeze (not the framework): JSON-RPC bridge protocol + @capsule/core API + pinned QuickJS-ng version. Semver + a protocol-version field.
    • Guarantees: capsule.lock pins the shell per project (reproducible); publish a compat matrix (CLI ⇄ shell ⇄ core ⇄ QuickJS ⇄ min WebView); CI builds every template AND runs each route bundle in real QuickJS per release. Framework version is documented as out-of-scope for Capsule compat.

    CLI distribution & self-update¶

    • Prefer project-local CLI (@capsule/cli devDependency, run via pnpm capsule) → version pinned per project, reproducible. Global install stays for capsule init.
    • No silent auto-update. Add an update-notifier ("update available → npm i -g @capsule/cli@x").
    • capsule upgrade bumps @capsule/core + shell in a project and rewrites capsule.lock (explicit). capsule doctor reports CLI/core/shell/QuickJS versions + compat.

    Adding Capsule to an existing web project — CLI-assisted (planned)¶

    • capsule dev/build already wrap any bundler (web.buildCommand/devCommand + transparent proxy).
    • A capsule init in an existing dir (or capsule integrate): detect bundler/framework, skip UI scaffold, generate capsule.config.ts (+ build/dev commands), add @capsule/core, run capsule add android. Developer only owns: static build output dir + dev/build commands.
