    Testing¶

    Capsule ships an opt-in test harness so a generated app can be tested at every layer that matters — from pure route handlers up to the real WebView on a device — without the developer wiring a toolchain by hand.

    Opt in at scaffold time, exactly like Tailwind: 

    capsule init my-app --template react-ts --test vitest
    Omitting --test shows a prompt (None / Vitest); None is the default and ships zero test files. Mirror of --css none|tailwind.

    Framework support¶

    Wired for all seven templates. The agnostic tiers (route-contract, route units, QuickJS-fidelity, integration) are identical everywhere; only the component test + vitest config are framework-specific.

    Framework Component test Notes
    react-ts ✅ @testing-library/react
    vue-ts ✅ @testing-library/vue
    svelte-ts ✅ @testing-library/svelte Vitest projects split (see wiring notes)
    vanilla-ts / vanilla-js ✅ raw DOM loads index.html, imports main, clicks by id
    jquery-bootstrap ✅ raw DOM native .click() fires jQuery's delegated handlers
    angular-ts ⏳ agnostic tiers only TestBed/analog component test is a follow-up

    Why layered¶

    Manual device testing (install → launch → screenshot → eyeball) is slow, token-/time-expensive, and flaky. Almost everything it checks is actually deterministic and can be asserted off-device in milliseconds. Each layer below catches a distinct failure class; only the last genuinely needs a device.

    Tier File (react-ts) Runtime Catches
    1 — Route contract src/test/route-contract.test.ts Vitest (node) A bridge.call('x') / fetch('/api/y') with no handler file (the 404 class) — statically, before build
    1 — Route units src/test/routes.test.ts Vitest (node) Handler logic — pure functions, no bridge/server
    2 — Component src/test/app.test.tsx Vitest (jsdom) UI wiring — renders <App/> against @capsule/core's FakeBridge; tab nav, async result plumbing
    3 — QuickJS fidelity src/test/quickjs.test.ts Vitest (node) + quickjs-emscripten "works in dev Node sidecar, breaks in embedded QuickJS" — bundles routes like capsule build, runs dispatch/handleHttpRequest in a real QuickJS, asserts fetch is absent
    — Integration (HML) src/test/integration.test.ts Vitest (node) Live backend — gated on CAPSULE_API_BASE, skipped by default so CI stays hermetic
    4 — On-device smoke app/src/androidTest/.../SmokeTest.kt Gradle connectedAndroidTest (Espresso-Web) Blank screen / WebView-attach / asset-load / JS crash — the one class only a real device/emulator shows

    Running¶

    capsule test                 # tiers 1–3 + integration (one-shot, hermetic)
capsule test --watch         # vitest watch mode
capsule test routes          # extra args pass through to vitest (filters/flags)

CAPSULE_API_BASE=https://hml.example.com capsule test   # also runs the HML test

# Tier 4 (needs a device/emulator):
#   debug   → run `capsule dev` first (loads the dev server via adb reverse)
#   release → self-contained (embedded bundle)
cd .capsule/android && ./gradlew :app:connectedDebugAndroidTest

    How it's wired (for maintainers)¶

    • Injector: packages/cli/src/testing.ts → applyTesting(projectDir, template). Copies assets/testing/_shared/ (the agnostic tiers, identical everywhere) then assets/testing/<framework>/ (vitest config + setup + component test) into the project, and patches package.json with test scripts + SHARED_DEPS + FRAMEWORK_DEPS[template]. Mirrors tailwind.ts. Called from init.ts when --test vitest (or the prompt) is chosen; falls through with a notice otherwise.
    • Component-test mock: each test does vi.mock('@capsule/core', …) returning a fresh FakeBridge as the bridge export, then reads it back via the mocked import (const fake = bridge as FakeBridge) — no __fake export hack, no hoisting trap. Vanilla/jQuery load index.html into jsdom and import main so the real handlers attach, then click by id.
    • Tier-3 detail: the QuickJS test runs in the node Vitest environment (// @vitest-environment node) — esbuild's TextEncoder instanceof Uint8Array invariant fails under jsdom. It re-creates the CLI's bundleRoutes() IIFE so it exercises the same dispatch contract Kotlin calls.
    • Svelte uses Vitest projects: svelteTesting() forces resolve.conditions: ['browser'] (so components get their client build), which would also make quickjs-emscripten load its network-fetching browser WASM. So the component test runs in a browser-conditioned jsdom project and the agnostic tiers run in a plain Node project. Other frameworks don't need this.
    • Tier-4 generator: sync.ts writes SmokeTest.kt + androidTest deps (espresso-web, ext-junit, runner) + testInstrumentationRunner on every sync. The assertion is content-agnostic (non-empty body text via a Hamcrest-1.3-safe matcher) because .capsule/android is regenerated each sync and can't be hand-tailored. Espresso pins Hamcrest 1.3 — avoid 2.x matchers (matchesPattern, blankOrNullString).

    Verification status (2026-06-12)¶

    • Tiers 1–3 + integration: PASS in every wired framework, each verified by injecting into its *-from-template example and running vitest: react / vue / svelte 12 passed, vanilla-ts / vanilla-js / jquery 11 passed, angular 9 passed (agnostic tiers, no component test) — 1 skipped (integration) in each. The contract test was proven to fail with Missing JSON-RPC route file(s): hello when hello.ts is removed.
    • capsule test + the applyTesting injector: verified end-to-end (command runs the suite; injector copies _shared + framework files and merges scripts + deps).
    • Tier 4: assembleDebugAndroidTest builds green; the on-device mechanism is proven (Espresso-Web launched MainActivity and read the live DOM via getText()). A fully-green connectedAndroidTest against a feature app (react-ts-native) is intermittent due to instrumentation/emulator state (NoActivityResumedException, post-test app uninstall) on a long-running session — not a scaffold defect.

    Follow-ups¶

    • Angular component test. Angular ships the agnostic tiers only. A component test needs Angular's TestBed wired into Vitest — e.g. @analogjs/vite-plugin-angular
    • a setup that calls initTestEnvironment, then @testing-library/angular's render(AppComponent). Add it under assets/testing/angular-ts/ and the deps to FRAMEWORK_DEPS['angular-ts'].
    • Tier-4 hardening for permission-requesting / slow-boot apps: a GrantPermissionRule (from config.android.permissions) and/or a launch retry to make connectedAndroidTest robust against NoActivityResumedException.
    • AI / agents testing (Phase 3 spike onward) maps onto these same tiers via a FakeAiProvider / scripted FakeLlm — the model is a provider behind the bridge, so the agent loop is deterministic given a scripted sequence of model responses. Tier 1 asserts tool-registry wiring + routing logic; Tier 2 renders against a canned ai.generate; Tier 3 runs the agent loop in real QuickJS with inference stubbed; the integration tier (gated on CAPSULE_AI_*) and Tier-4 device smoke assert structure not content against a live model (valid tool-call JSON, termination, token/latency budgets). See ../decisions/0003-ai-and-agents.md § Testing.

    Proxy bug fixed this session (dev-proxy-server.ts forwardInjectHtml): the non-Vite dev proxy buffered the bundler's HTML to inject <script src="/__capsule.js">, but did so assuming uncompressed bytes. Real browsers and the on-device WebView send Accept-Encoding: gzip; webpack-dev-server (default compress: true) then gzips the HTML. This bug would have broken all non-Vite examples in capsule dev on a real device/emulator, not just in-browser.

    Test order recommendation¶

    Group 0.1 (react-from-template) browser-dev → emulator-dev → emulator-release
Group 0 remaining (0.2–0.7) browser-dev only first pass
Group 2 (non-Vite) browser-dev — validates proxy
Group 1 (custom React) emulator-dev — validates full native API coverage
All groups emulator-release → device-release

    Start with react-from-template as it has the simplest surface area and covers the entire chain (Vite + sidecar + routes).
