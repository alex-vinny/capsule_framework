# Capsule Framework — `capsule.lock` Specification

> The lock file pins every resolved native dependency so builds are reproducible across machines and CI. Always commit it. Never hand-edit it.

---

## Why a Lock File

`capsule.config.ts` expresses *intent* (e.g. `shellVersion: '^1.4.0'`). `capsule.lock` records the *exact resolved versions* that were actually used — specific AAR URLs, hashes, and compatibility metadata. This is the same pattern as `package-lock.json` / `pnpm-lock.yaml` / `Podfile.lock`.

```
capsule.config.ts    →  "I want @capsule/camera ^2.0.0"
capsule.lock         →  "Resolved to 2.1.3, SHA-256: abc123, from https://..."
```

CI always runs `capsule sync --frozen-lockfile` which fails if the lock is stale, making divergence impossible.

---

## Format: YAML

YAML was chosen over JSON because:
- Diffs are human-readable (important: lock changes are code-reviewed)
- Comments are allowed (the CLI adds context comments)
- Less syntactic noise than JSON for this kind of structured data

---

## Full Schema with Example

```yaml
# capsule.lock
# Generated by @capsule/cli. Do not edit manually.
# Regenerate with: capsule sync
# Verify in CI with: capsule sync --frozen-lockfile

lockfileVersion: 1

# ── Capsule shell (the native binary dependency) ────────────────────────────
shell:
  android:
    version: "1.4.2"                        # exact version, never a range
    mavenCoordinate: "dev.capsule:capsule-android:1.4.2"
    aarUrl: "https://maven.capsule.dev/dev/capsule/capsule-android/1.4.2/capsule-android-1.4.2.aar"
    sha256: "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
    targetSdk: 35
    minSdk: 21         # minimum supported by this shell version
    kotlinVersion: "2.0.21"

plugins:
```

## Field Reference

### `shell` section

| Field | Description |
|-------|-------------|
| `version` | Exact semver of the Capsule native shell. Always a fixed version, never a range. |
| `mavenCoordinate` | `groupId:artifactId:version` — used in generated `build.gradle` |
| `aarUrl` / `xcframeworkUrl` | Canonical download URL |
| `sha256` | SHA-256 of the artifact — verified by `capsule sync` before use |
| `targetSdk` | Android targetSdk baked into this shell version |
| `minSdk` | Lowest Android version this shell supports |
| `deploymentTarget` | Minimum iOS version this shell supports |

The shell version determines which Android SDK and iOS deployment target the app targets. Updating the shell (via `capsule update`) may raise these values — the CLI reports the change and updates `capsule.config.ts` accordingly.

### `plugins` section

| Field | Description |
|-------|-------------|
| `trust` | `tier1` / `tier2` / `local` / `unverified` — set by CLI from npm scope, never by plugin itself |
| `requiresShell` | npm semver range — CLI errors if resolved shell version doesn't satisfy this |
| `sha256` | Artifact integrity hash — verified before extraction |
| `sourceHash` | For local plugins: hash of the source tree — `capsule sync` warns if it changed since last lock |
| `android.minSdk` | Plugin's minimum Android version requirement — see conflict resolution below |

### `build` section

Pins the Gradle distribution URL and hash so every machine downloads the exact same wrapper. Also records the expected Node.js and pnpm versions for informational checks.

## Plugin minSdk Conflict Resolution

When a source plugin declares a higher `minSdk` than the app:

```yaml
# App capsule.config.ts has:  android.minSdk: 26
# Plugin capsule-plugin.json has: android.minSdk: 30
```

**CLI behavior**:

```
⚠ Warning: Plugin "my-scanner" requires minSdk 30, but the app targets minSdk 26.
  Devices running Android 8.0–9.x (API 26–29) will not load this plugin.
  The plugin will be silently ignored on those devices.
  To suppress this warning: set android.minSdk: 30 in capsule.config.ts
  To understand impact: capsule codesync devices --platform android
```

The plugin is **not removed** — it is conditionally loaded at runtime only on devices that meet its minSdk. On older devices, the plugin's bridge methods return a `3001 PLUGIN_UNAVAILABLE` error. The web bridge should handle this gracefully.

Scenarios where a plugin **genuinely cannot support older Android versions**:
- Uses `CameraX` APIs added in API 28+
- Uses biometric authentication (BiometricPrompt, API 28+)
- Uses Foreground Service types declared in API 29+
- Uses exact alarm scheduling (API 31+)
- Uses Bluetooth LE with new permission model (API 31+)

In these cases the warning is accurate — the plugin truly does not work on older devices and the developer should either raise the app's minSdk or accept the limitation.

## Lifecycle: When the Lock File Changes

| Action | Lock file change |
|--------|-----------------|
| `capsule init` | Created from `capsule.config.ts` with latest compatible versions |
| `capsule add android\|ios` | Shell entry added for the new platform |
| `capsule update` | Shell version bumped to latest compatible; `sha256` updated. Core SDK capabilities update with the shell. |
| `npm install @capsule-community/maps` + `capsule sync` | Community integration entry added with resolved version + hashes |
| `npm update @capsule-community/maps` + `capsule sync` | Integration entry version + hashes updated |
| `capsule eject @capsule-community/maps` | Binary integration entry replaced with local source entry |
| Editing `capsule-plugin.json` in a source integration | `sourceHash` updated on next `capsule sync` |
| `capsule sync --frozen-lockfile` | **No change** — fails if lock would need to change |

## Shell Version Registry

`capsule sync` and `capsule update` resolve version ranges by querying the **GitHub Releases API** for the `capsule-framework/capsule` repository. This requires zero Capsule-specific infrastructure — GitHub Releases is the canonical source of truth for shell versions.

**Resolution process:**
```
GET https://api.github.com/repos/capsule-framework/capsule/releases
→ returns list of releases tagged v1.4.2, v1.4.1, v1.3.0, ...
```

Each release attaches a `release.json` asset containing full metadata for that version:
```json
{
  "version": "1.4.2",
  "android": {
    "aarUrl": "https://github.com/capsule-framework/capsule/releases/download/v1.4.2/capsule-android-1.4.2.aar",
    "sha256": "e3b0c44298fc1c...",
    "targetSdk": 35,
    "minSdk": 21,
    "kotlinVersion": "2.0.21",
    "agpVersion": "8.7.0"
  },
  "ios": {
    "xcframeworkUrl": "https://github.com/capsule-framework/capsule/releases/download/v1.4.2/CapsuleShell.xcframework.zip",
    "sha256": "a665a45920422f...",
    "deploymentTarget": "16.0",
    "swiftVersion": "5.9"
  }
}
```

**Rate limiting:** The CLI caches the release list locally (TTL 1 hour, stored in `~/.capsule/cache/releases.json`). Authenticated requests (`GITHUB_TOKEN` env var) raise the limit from 60 to 5000 req/hour — relevant only for CI pipelines making many requests. For most teams, the unauthenticated limit is never reached.

**Offline mode:** If the GitHub API is unreachable and a cached list exists, the CLI uses the cache with a warning. If no cache exists, `capsule sync` fails with a clear network error — not a silent fallback to a wrong version.

**Future path (Phase 8+):** `registry.capsule.dev` will be added as a thin proxy in front of GitHub Releases (the base GitHub-Releases shell registry lands in Phase 8 — Ecosystem), enabling: deprecation notices, version yanking without deleting releases, first-party CDN routing, and analytics. The lock file format and resolution semantics are unchanged — only the query endpoint changes. The CLI will support both via a `registryUrl` setting.

## Auto-Creating the Lock File

When `capsule sync` is run and no `capsule.lock` exists (e.g. after cloning a repo that predates locking, or on `capsule init`):

```
1. Read capsule.config.ts
2. Resolve all version ranges to the latest compatible versions
   → shell: resolve '^1.0.0' to the latest 1.x release
   → plugins: resolve '^2.0.0' to the latest 2.x release
3. Fetch SHA-256 hashes for each resolved artifact
4. Write capsule.lock
5. Print: "capsule.lock created — commit this file"
```

For existing projects migrating to lock-file-based workflow:
```bash
capsule sync          # creates capsule.lock from current capsule.config.ts
git add capsule.lock
git commit -m "chore: add capsule.lock"
```

## CI Usage

```yaml
# .github/workflows/build.yml
- name: Sync capsule wrappers
  run: capsule sync --frozen-lockfile
  # Fails with exit code 1 if capsule.lock is out of date.
  # This catches: "developer updated capsule.config.ts but forgot to run capsule sync"

- name: Build Android
  run: capsule build android --release
```

`--frozen-lockfile` never writes to disk. It only validates that the current `capsule.lock` matches what `capsule sync` would produce from `capsule.config.ts`. If there is a mismatch, it prints a diff and exits non-zero.

## `.gitignore` Rules

```gitignore
# Generated by capsule — do not commit
.capsule/

# DO commit — this is the lock file
# capsule.lock   ← no entry here, it must be committed
```

The CLI's `capsule init` writes this `.gitignore` block automatically.

## Version Format: npm Semver

All version constraints in `capsule.config.ts` use **npm semver syntax** — the same format as `package.json` `dependencies`. This is intentional: same tooling, same mental model, no new syntax to learn.

```typescript
// capsule.config.ts — version constraints (before resolution)
shellVersion: '^1.4.0'   // any 1.x.x >= 1.4.0
shellVersion: '~1.4.0'   // any 1.4.x >= 1.4.0
shellVersion: '1.4.2'    // exact pin

// capsule.lock — always exact after resolution
shell.android.version: "1.4.2"   // never a range
```

`min_native_version` in CodeSync bundles (see `../contributing/codesync-internals.md`) also uses npm semver:
```bash
capsule codesync publish --min-native-version ">=1.4.0"
# Devices running shell < 1.4.0 will not receive this bundle
```

The native client evaluates the constraint using a bundled semver library (same logic as npm's `semver` package).
