# Capsule Framework — Issues, Solutions & Prior Art

> Raised against `principles.md`. Each issue includes severity, recommended solution, and relevant existing projects to adopt or study.

## Issue 1 — `.capsule/` Directory Commit Strategy is Ambiguous

**Severity: Medium**

### Problem
The doc says "commit it for reproducibility, treat it like a lock file." This causes:
- Every `capsule sync` produces noisy, meaningless diffs
- CI always regenerates it anyway — committed state drifts silently
- Developers fight the `.gitignore` default (do I commit or not?)

### Recommended Solution
**Gitignore `.capsule/` by default. Commit only `capsule.lock`.**

```
# .gitignore (generated by capsule init)
.capsule/

# capsule.lock — DO commit this
```

`capsule.lock` records the resolved versions of the native capsule and all plugins (like `package-lock.json`). CI runs `capsule sync` as an explicit pre-build step using the lock file to reproduce the exact same generated wrappers deterministically.

```bash
# CI pipeline
capsule sync --frozen-lockfile   # fails if lock is out of date
capsule build android
```

### Prior Art
- **Gradle wrapper** (`gradlew`) — generated but committed because it's a bootstrap shim, not generated output
- **`package-lock.json`** — lock the versions, regenerate the artifacts
- **CocoaPods `Podfile.lock`** — same pattern for iOS deps

## Issue 2 — Bridge Protocol Underspecified

**Severity: High** — affects every plugin author and the entire SDK contract

### Problem
The current spec only covers request/response:
```
window.__capsule.call('camera.capture', { quality: 0.8 })
window.__capsule.resolve(callId, { path: '/tmp/img.jpg' })
```
Missing:
- **Streaming** (video frames, file download progress, sensor data)
- **Cancellation** (user navigates away mid-operation)
- **Error taxonomy** (permission denied vs hardware error vs timeout — all look the same)
- **Event subscriptions** (native pushes to web without a web-initiated call)

### Recommended Solution
**Adopt JSON-RPC 2.0 as the bridge wire format**, extended with Capsule-specific envelope fields.

```typescript
// Web → Native (request)
{
  jsonrpc: '2.0',
  id: 'uuid-v4',           // callId
  method: 'camera.capture',
  params: { quality: 0.8 }
}

// Native → Web (success)
{
  jsonrpc: '2.0',
  id: 'uuid-v4',
  result: { path: '/tmp/img.jpg' }
}

// Native → Web (error — typed)
{
  jsonrpc: '2.0',
  id: 'uuid-v4',
  error: {
    code: 4001,              // Capsule error registry
    message: 'PERMISSION_DENIED',
    data: { permission: 'CAMERA' }
  }
}

// Native → Web (event / stream chunk — JSON-RPC "notification")
// IMPORTANT: notifications omit the `id` field entirely.
// id: null is NOT a notification — it is a response to a null-id request.
{
  jsonrpc: '2.0',
  method: 'push.messageReceived',
  params: { title: '...', body: '...' }
}
```

**Capsule Error Code Registry** (define upfront):

| Range | Category |
|-------|----------|
| 1xxx | Framework errors (bridge timeout, serialization) |
| 2xxx | Permission errors |
| 3xxx | Hardware errors (camera unavailable) |
| 4xxx | Plugin-specific errors |
| 5xxx | User cancellation |

**Cancellation** via a `capsule.cancel(callId)` call — native must honor it for any long-running operation.

### Prior Art
- **JSON-RPC 2.0 spec** — `jsonrpc.org` — battle-tested, tooling exists, readable
- **Capacitor's bridge** (`@capacitor/core`) — study `src/bridge.ts` for real-world handling of callbacks and events
- **`@trpc/server`** — for inspiration on typed procedure definitions that could generate bridge manifests

## Issue 3 — Hot Reload on Physical Devices is Fragile

**Severity: Medium** — major DX pain point, especially in corporate environments

### Problem
"Same WiFi: load from machine's LAN IP" fails when:
- Corporate/guest WiFi isolates clients (very common)
- Dynamic IP requires manual reconfiguration
- Developer switches networks without noticing

### Recommended Solution
**Build tunneling into `capsule dev` as a first-class mode.**

```bash
capsule dev                   # LAN mode (default, fastest)
capsule dev --tunnel          # HTTPS tunnel (works everywhere)
capsule dev --qr              # Display QR code for device pairing
```

The `--tunnel` flag should:
1. Use **Cloudflare Tunnel** (free tier, no account needed for ephemeral tunnels via `cloudflared`) or a self-hosted tunnel endpoint
2. Generate a `https://random.trycloudflare.com` URL
3. Display a QR code in the terminal — scan with the device to set the dev server URL

**Why Cloudflare over ngrok**: Cloudflare Tunnel's ephemeral mode requires no account, no auth token, no rate limit on free tier.

```bash
# capsule dev --tunnel internals
npx cloudflared tunnel --url http://localhost:5173
# → https://abc123.trycloudflare.com
# → QR code rendered in terminal via qrcode-terminal npm package
```

### Prior Art
- **Expo CLI** (`expo start --tunnel`) — uses `@expo/ngrok` internally, same QR pattern
- **`cloudflared`** — `github.com/cloudflare/cloudflared` — single binary, works on CI too
- **`qrcode-terminal`** npm package — used by Expo, renders QR in terminal

## Issue 4 — No Signing & Distribution Story

**Severity: High** — blocks real-world production use

### Problem
Build pipeline ends at `.apk`. Real releases require:
- **Android**: signing with a keystore, aligning, uploading to Play Store
- **iOS**: provisioning profiles, certificates, notarization, App Store Connect upload

If developers must do this manually, Capsule's DX promise breaks at the last mile.

### Recommended Solution
**Integrate Fastlane as the signing/distribution backend**, invoked by the Capsule CLI.

```bash
capsule sign android            # configure signing (stores config, not keystore)
capsule build android --release # builds + signs
capsule publish android         # uploads to Play Store (via Fastlane supply)
capsule publish ios             # uploads to App Store (via Fastlane deliver)
```

Capsule wraps Fastlane so developers never write a `Fastfile`. The CLI generates it from `capsule.config.ts`.

**Keystore management**: Never store the keystore in the project. Capsule should:
1. Generate a keystore on first `capsule sign android`
2. Encrypt it with a passphrase
3. Optionally push to a secrets backend (env var, 1Password, GitHub Secrets)

```typescript
// capsule.config.ts signing block
android: {
  signing: {
    storeFile: process.env.CAPSULE_KEYSTORE_PATH,
    storePassword: process.env.CAPSULE_KEYSTORE_PASS,
    keyAlias: process.env.CAPSULE_KEY_ALIAS,
    keyPassword: process.env.CAPSULE_KEY_PASS
  }
}
```

### Prior Art
- **Fastlane** (`fastlane.tools`) — `github.com/fastlane/fastlane` — industry standard, handles both platforms
- **Fastlane Match** — syncs certificates/profiles via a private git repo or S3
- **EAS Build** (Expo Application Services) — study how they abstract signing from developers, good UX reference
- **Gradle signing config** — `signingConfigs` block in `build.gradle`, already standard

## Issue 5 — Community Plugin Trust Model is Missing

**Severity: High** — architectural integrity risk

### Problem
The document's core promise is "the shell is a binary dependency, developers never touch native code." A community plugin can completely bypass this — it can include arbitrary Kotlin/Swift code, request any permission, execute any native API.

There is no stated policy on:
- What native code community plugins are allowed to include
- How plugin quality/safety is vetted
- Whether a rogue plugin can escalate privileges beyond what `capsule.config.ts` declares

### Recommended Solution
**Define a Plugin Trust Tier system with enforcement at install time:**

```
Tier 1 — @capsule/* (official)
  - Maintained by Capsule team
  - Full native access
  - Code audited, signed
  - Example: @capsule/wasm (extends the shell with the WASM runtime for code-logic integrations)

Tier 2 — @capsule-community/* (verified)
  - Third-party, reviewed by Capsule team
  - Native code declared in plugin manifest
  - Automatically flagged in capsule.config.ts

Tier 3 — Unverified plugins
  - Require explicit opt-in in capsule.config.ts (see syntax below)
  - CLI warns on install and on every build
```

**Plugin manifest** (`capsule-plugin.json`) — required for any plugin with native code:

```json
{
  "name": "@capsule-community/stripe",
  "nativePermissions": [],
  "nativePlatforms": {
    "android": { "aar": "https://maven.../stripe.aar" },
    "ios": { "xcframework": "https://..." }
  }
}
```

> **Note**: `trustTier` is **not** self-declared in the manifest — a rogue plugin would simply claim Tier 1. The CLI determines the trust tier from the npm package scope:
> - `@capsule/*` → Tier 1 (hardcoded in CLI) — first-party plugins like `@capsule/wasm` that extend the shell with optional native capabilities
> - `@capsule-community/*` → Tier 2 (verified by Capsule team, signed release)
> - anything else → Tier 3 (unverified, explicit opt-in required)

**Tier 3 opt-in syntax in `capsule.config.ts`**:

```typescript
plugins: [
  '@capsule/wasm',                         // Tier 1 — no opt-in needed
  '@capsule-community/stripe',             // Tier 2 — no opt-in needed

  // Local source plugins — always trusted (you own the source)
  './capsule-plugins/my-scanner',          // shorthand, local: true implied
  { path: './capsule-plugins/my-scanner', local: true },  // explicit form

  // Third-party npm plugin outside @capsule or @capsule-community scopes
  // MUST use object form with trust: 'unverified'
  // CLI prints a warning on every build until this is acknowledged
  { path: 'some-npm-plugin', local: false, trust: 'unverified' }
]
```

The `local: true` flag signals the plugin is compiled from source in your project. It is **always implied** for `./` paths and **always false** for bare npm package names. The object form exists for cases where you need to be explicit or add `trust: 'unverified'`.

The CLI reads the manifest at `capsule sync` and:
1. Merges declared permissions into the generated `AndroidManifest.xml` / `Info.plist`
2. Rejects undeclared permissions that weren't in `capsule.config.ts`
3. Warns if a plugin requests more permissions than the app declared

### Prior Art
- **npm provenance** (`--provenance` flag) — ties npm packages to their source git commit via Sigstore
- **Capacitor plugin registry** — `capacitorjs.com/docs/plugins` — unofficial but curated list
- **Android Play Protect** — permission declaration model is already what this borrows from
- **VS Code Extension Marketplace** — trust tiers and capability declarations are the model to follow

## Issue 6 — iOS Phase Deferred but Config Already Exists

**Severity: Low** — documentation gap, easy to handle

### Problem
Phase 1 is Android-only, but `capsule.config.ts` already shows `ios:` config keys. A Phase 1 developer adding iOS config gets either silent ignoring or a confusing error.

### Recommended Solution
**CLI should surface clear platform-availability errors with upgrade path:**

```bash
$ capsule add ios
✖ iOS support is not available in @capsule/cli@1.x
  → Upgrade to @capsule/cli@2.x when iOS support ships
  → Track progress: github.com/capsule-framework/capsule/milestone/3
```

And in `capsule.config.ts`, mark the iOS block with a JSDoc that the TS language server will show:

```typescript
ios: {
  /** @experimental Available in Capsule Phase 4+ */
  deployment: '16.0',
}
```

## Issue 7 — Server Readiness Race Condition *(Known and Solved)*

**Severity: High** — would cause a blank/ERR_CONNECTION_REFUSED screen on launch without mitigation

### Problem (was)
Phase 2 adds an embedded HTTP server (`NanoHTTPD` on Android). The `WebView` navigates to `http://127.0.0.1:{port}/` on launch. If the WebView navigates before the server is bound and listening, the user sees `ERR_CONNECTION_REFUSED`.

### Solution (decided in ADR-001)
`CapsuleRuntime` owns the startup sequence. `CapsuleActivity` delegates entirely to it:

1. Splash screen shows immediately (zero blank frame)
2. `CapsuleRuntime.start()` binds NanoHTTPD and (if routes exist) evaluates the QuickJS server bundle
3. On ready → WebView navigates to `http://127.0.0.1:{port}/` and splash hides
4. On timeout (default 3 s, configurable via `server.timeout` in `capsule.config.ts`) → error screen with a retry button

The `SplashController` interface and `FakeSplashController` fake enable this entire flow to be tested in pure JVM unit tests — no device or emulator needed.

### Prior Art
- **React Native's splash pattern** — `AppRegistry.registerComponent` deferred until JS bundle is loaded
- **Capacitor's `WebViewAssetLoader`** — avoids this problem by serving from a pre-bound URL, but Capsule's embedded server approach gives more capability in exchange for managing readiness explicitly

## Issue 8 — Crash Loop Recovery *(Known and Solved)*

**Severity: High** — without mitigation, a bad OTA (codeSync) deploy could permanently brick the app until a store update

### Problem (was)
`codeSync` can push a new web bundle or server bundle to the device. If the new bundle crashes on launch (runtime error, bad JS, incompatible API), the app crashes on every open. The user has no recovery path short of reinstalling.

### Solution (decided in ADR-001)
`CapsuleRuntime` tracks start failures. **Three failures within 60 seconds** triggers automatic rollback to the previous known-good bundle zip. The rollback is silent — the user sees a brief restart, not an error.

- `CodeSyncManager` interface owns the rollback logic
- The "bundle" is always atomic: `www/ + server/bundle.js` together in one zip; they are never deployed independently
- The crash loop counter resets on a successful startup
- Tested via `FakeCapsuleServer.crashesAfterRequests(1)` in pure JVM unit tests

This means a bad codeSync deploy is self-healing. Developers and users never see the rollback unless they inspect logs.
